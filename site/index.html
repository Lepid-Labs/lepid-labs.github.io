How we build

01

Nothing important lives only in a hosted service

Content, configuration, and indexes are files you can version. A tool of ours can disappear and leave your work intact.

02

The host stays in charge

Our tools mount into the page, repository, or workflow you already have. It keeps its URL, its history, its search, and its data. We supply the part it does not have.

03

One thing each

Every library does one job and can be reasoned about on its own. Products compose them; nothing depends on the composition.

Released

Weft

Public MIT

A documentation graph browser that lives in the repository alongside the code. Design docs, specs, API definitions, and diagrams become nodes with typed, anchor-level relationships between them. Any document is an entry point; navigation is the product.

It runs as a CLI over a local checkout, or embeds into any page as a single script. This site's FAQ and Docs pages are Weft embedded.

<script src="weft.iife.js"></script>
<script>
  Weft.mountWeft('#docs', { repo: 'acme/project' });
</script>

In the works

Four areas, all built the same way. Each appears here with a name when it is ready for someone other than us.

Developer tooling

A code indexer that gives editors and agents a structural view of a repository, and the pieces around Weft that make a documentation graph useful beyond the browser.

Knowledge and agents

A knowledge graph for what a team knows, agent frameworks that read the same graph people do, and voice as an interface to both.

Platform

The services a small lab needs to run its own things: authentication and single sign-on, a deployment backplane, a project dashboard. Built for ourselves first.

Creative tools

Writing tools, tabletop game aids, and image generation utilities. The same method, a different audience.
